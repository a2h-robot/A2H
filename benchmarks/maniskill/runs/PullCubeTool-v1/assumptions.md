# Assumptions of pipeline.py (PullCubeTool-v1)

Line numbers refer to `pipeline.py` as committed after Phase 1 (s0 = 1.0). They are updated in each
round's notes at the bottom.

| # | Category | Assumption | Code that relies on it |
|---|---|---|---|
| A1 | orientation | The tool lies flat, upright (not flipped), so the hook points along the tool's +y axis and a single yaw angle describes its pose. | `yaw_of`/`detect_avg` (l.19-28) keep only yaw; `tool_y = cube_y - ...` (l.66) puts the handle on the cube's -y side because the hook is assumed to point +y. |
| A2 | orientation | The tool's yaw is near 0 (handle pointing away from the robot), so rotating it in the hand to world yaw 0 is a small wrist motion that the planner always finds. | `tcp_for_tool(..., yaw=0.0)` (l.59-60) and every call at l.68-74. |
| A3 | object_position | The tool lies on the table surface (z = 0), so the handle centre is at z = 0.025. | `grip_z = 0.025` (l.43); `tool_z = tool_p[2] + 0.004` (l.67). |
| A4 | object_position | The grasp point 4 cm along the handle from its free end is free and reachable. | `grip_xy = ... [0.04, 0]` (l.41). |
| A5 | object_position | The cube is in front of the robot and on the -y side of nothing: the region on the cube's -y side (where the handle is lowered) and on its far (+x) side (where the hook is lowered) is empty table. | `tool_x`, `tool_y` (l.65-66); lowering at l.69. |
| A6 | object_position | Pulling the cube straight along -x to x = -0.15 is enough to bring it within 0.6 m of the base, i.e. the cube's lateral offset \|y\| is small (< ~0.37 m). | `target_cube_x = -0.15`, pull along -x only (l.71-74). |
| A7 | object_position | Cube and tool are within the arm's reach; the hook placement for the farthest cube (x = 0.25) is reachable at table height. | l.68-69. |
| A8 | object_motion | The cube does not move between the single initial detection and the end of the pull; the tool does not move between its detection and the grasp. | `cube_p` is detected once at l.37 and never re-detected; open-loop pull (l.74). |
| A9 | obstacle | The paths are free: lifting to 0.15 m, the transfer at 0.15 m, the straight descent, and the straight pull along -x cross no other object. `move_to` is called without `avoid`. | l.45-52, l.68-74. |
| A10 | dynamics | The tool does not slip or rotate in the fingers when lifted (it is held 4 cm from its end, far from its centre of mass) or while pulling; `tcp_T_tool` measured once after the lift stays valid. | `tcp_T_tool` (l.55-57) used for every later target. |
| A11 | dynamics | The cube slides on the table under a gentle push of the hook: its mass and friction are small enough that the held tool can drag it without slipping in the grasp. | l.74. |
| A12 | dynamics | The cube stays in the corner between hook and handle during the pull (it does not slide off the hook's tip). | pull along -x only, hook covers cube y +-0.03 (l.66). |
| A13 | perception | Averaging 15-20 noisy detections (1 cm / 3 deg) is accurate enough for 1.2-1.5 cm clearances. Nothing confusable is in the scene, and `detect` returns the right object. | `detect_avg` (l.23-28), clearances 0.012 / 0.015 (l.65-66). |
| A14 | camera / lighting / color | No image is used; perception is pose-based. | (no code uses `camera_frame`) |
| A15 | outcome | Every step succeeds; return values of `move_to` are ignored and there is no check that the cube actually moved, no retry. | l.44-74 ignore return values; only `gripper_holding` is checked (l.48). |

## Round notes

- **Round 1 (v1, orientation, accepted):** attacked A1. A first design (tool yaw rotated by 180 deg, `variations/rejected_r1a.yaml.txt`) was rejected by the break gate (s_break 0.9): yaw was already handled. A flipped tool (roll 180 deg) broke the pipeline (s_break 0.0). Fixed by using the full rotation; A1 now reads "the tool lies flat (either face up)". A2 is retired.
- **Round 2 (v2, object_motion, accepted):** attacked A8. A first design (1.5 cm push, `variations/rejected_r2a.yaml.txt`) was rejected by the break gate (s_break 1.0). A 13 cm push broke it (s_break 0.0). Fixed by waiting for the cube to be still and re-detecting it before placement. While repairing, A10 was found violated on the base task itself (the tool pivots up to 35 deg in the fingers during fast carries); fixed by slow carries, re-measuring the tool in the hand after every carry, and commanding the tool's level pose. A8 now reads "the cube does not move after the last re-detection (during descent and pull)".
- **Round 3 (v3 unsolved, v4 accepted, obstacle):** attacked A9. v3 (block directly behind a far cube) broke the pipeline but has no detour within reach (oracle 0.0, see `v3.yaml` `unsolved_reason`); marked unsolved. The repair added obstacle-aware stroke planning with the hand's footprint. v4 (block halfway down the lane, `parameter_tuning: true`) broke the round-2 pipeline (s_break 0.0) and is recovered (1.0). A9 now reads "detours are limited to: straight pull, sideways handle push then pull, with the tool level or tilted; obstacles are boxes from get_obstacles()". New assumption A16: the arm (links above the hand) never hits an obstacle; only the hand and fingers are checked. A17: the cube follows the tool exactly during a sideways push (no rotation off the handle).
- **Round 4 (v5, dynamics, accepted):** attacked A10. Heavy/high-friction cube and slippery tool did not break the pipeline (sweep in `logs/runs.jsonl`, variations `dyn_*`); a 1.0 kg tool did (s_break 0.0, oracle 0.0). Fixed with a test lift and a table-supported slide mode, straight-hop contact moves, a radial working frame and a reach check. A10 now reads "if the test lift shows < 12 deg pivot, the tool stays rigid during slow carries". New assumptions: A18 the robot base is at (-0.615, 0) and the horizontal reach near the table is 0.80 m (constants, not perceived); A19 the tool's geometry (handle 0.2 m, hook 0.05 x 0.1 m) is known, not measured.
- **Round 5 (v6, obstacle, accepted):** attacked A3 with a tool on a 6 cm platform. Rejected by the gate (s_break 1.0, `variations/rejected_r5a.*`): the hand's compliance still produced a grasp. Then attacked A4 with v6, a tall block beside the grasp point (s_break 0.0, oracle 0.0). The gate was delayed by about 22 h while the simulation host was offline. Fixed by choosing a clear grasp point (hand plus open fingers checked against obstacles), taking the grasp height from the perceived pose, and setting the tool down to regrasp when the clear point is not the usual one. s_recovered 1.0. A3 now reads "the tool rests on a surface; its height is perceived". A4 now reads "some point along the handle has a clear vertical approach, and a free spot exists nearby to set the tool down".
